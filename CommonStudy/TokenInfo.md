⇒ 서버가 자물쇠를 붙들고 있고 쿠키가 열쇠이기 때문에 요청 때마다 서버의 자물쇠(세션)과 클라이언트(열쇠)가 맞는 지 확인하는 과정을 거친다.

→ 이미 만들어진 자물쇠와 열쇠는 다른 인증에서 사용할 수 없기 때문에 확장성이 낮음

### A. Token 인증 방식

✅️ 토큰 기반 인증 방식

- Bearer Token을 얻기 위해서는

<aside>

1. 클라이언트가 서버에 로그인 요청을 보냄
2. 서버는 DB를 확인 → 인증 성공 시 → **사용자 정보**를 담은 토큰 생성
3. 서버가 클라이언트에게 **응답을 보낼 때 바디 혹은 헤더에 토큰을 담아** 전달

🚨 이때, 토큰은 HTTPS를 이용해서 전송 (토큰 도둑 방지)

1. 클라이언트는 해당 토큰을 로컬저장소 혹은 세션 저장소에 직접 저장

---

- 앞으로의 토큰 이용이 필요할 때
1. 클라이언트의 앞으로의 요청 때마다 헤더에 토큰을 담아서 전송
2. 서버는 이 토큰의 유효성 검사 과정을 통해서 인증 여부 판단
</aside>

- 토큰 기반으로 바뀌면서 좋아진 점

→ 브라우저의 역할이 필요 없음 ⇒ 클라이언트와 서버의 양방향으로 해결 가능

→ 사용자 정보가 토큰에 아예 저장되어 클라이언트와 서버 사이를 이동하므로 확장성 높음

### C. 토큰을 서버가 저장하지 않는다 했는데, 그럼 어떻게 확인해?(JWT)

: 서버가 클라이언트로 부터 요청을 받았을 때, 토큰을 생성하는데 서버는 이 토큰을 저장하지 않는다. 그래서 로그인 이후에 들어온 클라이언트의 요청이 들어올 때, 요청 받을 때마다 서버는 다음 확인 작업을 거친다.

1. 요청 헤더에서 토큰을 추출
2. 토큰 유효성 검증
3. 토큰에서 setSubject로 설정한 값 파싱
4. 인증된 사용자라고 판단하고 요청을 처리한다

→ 이렇게 3가지의 과정을 거쳐야 한다.

⇒ 코드 구현 필요함!

⇒ 필요한 파일 구성

1. JwtUtil → 토큰 검증 및 정보 파싱(꺼낸 토큰으로 진행)
2. JwtAuthenticationFilter → 요청마다 토큰 꺼내서 인증 처리
3. Securityconfig → 필터 등록(빈 등록)

### D. JWT 인증 흐름 정리

1. 클라이언트 → 서버 : POST로 서버에 이메일, 비밀번호 전송(로그인)
2. 서버의 확인 : 
    - 로그인 정보와 DB에 저장된 회원 정보를 비교하여 인증 확인 진행
    - 인증을 성공하면 JWT를 생성 ⇒ 3가지 구성 요소
    
    <aside>
    
    JWT = (header) . (payload) . (signature) 형태로 구성
    
    → header , payload는 Base64로 인코딩 된 형태
    
    → 헤더에는 토큰 타입이
    
    → 페이로드에는 데이터 정보들(넥네임, 나이, 이름)
    
    → 마지막 signature는 비밀 키(변조 방지)
    
    </aside>
    
3. 서버 → 클라이언트 : 위 JWT = header.payload.signature를 응답으로 넘김
4. 클라이언트가 JWT 로컬에 저장
5. 클라이언트 → 서버 : 앞으로 인증이 필요한 요청마다 헤더의 Auth부분에 JWT보냄
    
    로컬에 토큰이 저장되어 있기 때문에 헤더에 넣어서 보낼 수 있음.
    
6. 서버의 파싱 : 서버는 받은 JWT를 split(기준은 “.”)하여 3가지 구성요소를 얻어냄
    - header + payload는 다시 디코딩해서 json형태로 만들고
    - signature 검증
