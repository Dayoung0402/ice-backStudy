# “HTTP” VS “HTTPS”

---

## 1. HTTPS = HTTP + S(ecurity)

: http의 보안 저번으로 데이터 전송의 보안을 강화하기 위해서 암호화 된다. 

: 두 개의 프로토콜이 “완전히 다르다”라고 인식하는 것보다 HTTPS가 HTTP를 한 단계 업그레이드 시켜서 포장지를 씌운 것이라고 생각하면 된다. 단,  http포장지는 비닐 포장지로 안이 보일 수 있는 구조라면, https포장지는 강철 포장지인 정도…? (안을 볼 수 없다는 말)

## 2. 어떻게 암호화가 진행돼?

: 암호화 프로토콜을 사용하여서 통신을 암호화한다. 

→ 암호화 프로토콜은 Transport Layer Security(TLS)

→ 두 개의 서로 다른 키를 사용해서 두 당사자 간의 통신을 암호화

⇒ 개인 키(공개 키로 암호화된 정보를 해독하는 사용) + 공개 키(서버와 교류하는 클라이언트 모두가 사용 가능, 공개 키는 개인 키로만 해독 가능)

## 3. 암호화가 왜… 필요해?

: 일반 전달 프로토콜인 HTTP를 사용할 경우, 데이터를 전송할 때 네트워크를 지날 때 데이터 패킷으로 바뀌어서 전달되는데, 이 통신 과정에서 누구나 이 패킷을 가로채서 정보를 얻을 수 있기 때문에 보안의 문제가 발생할 수 있다.

→ 하지만 암호화하는 과정을 거친다면, 패킷을 가로챈다 하더라도 무의미한 문자를 받는다.

## 5. HTTPS를 [서버/클라이언트]로 전달하는 흐름

<aside>
📌

[ post 메소드를 이용해서 서버에 리소스를 전달한다고 가정]

1. 클라이언트 → 서버로의 요청

: 클라이언트가 서버로 post 요청을 보낸다. 이 요청 메세지 바디에는 json의 형태로

**{”content”=”dayoung”} 가 담겨있는데, 이 부분이 암호화된다.** 

1. **네크워크에서 암호환된 위의 데이터 전송**

**: 네트워크를 통해서 암호화된 데이터를 전달한다.**

1. **서버에서 데이터 복호화(복호화 : 암호를 푸는 행위)**

**: 서버가 위의 암호화된 데이터를 복호화화하고**

**이렇게 복호화된 메세지 바디는 원래의 형태를 띈다.**

원래의 형태 = {”content”=”dayoung”}

1. json 파싱

: 복호화된 데이터는 서버 어플리케이션에 의해서 파싱되어서 서버가 이를 데이터베이스에 저장하는 등의 적절한 처리를 할 수 있게 된다.
