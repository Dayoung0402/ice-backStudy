# “HTTP”

## 1. HTTP가 무엇인가?

- HTTP : 웹 상에서 클라이언트와 서버가 데이터를 주고 받을 때 사용하는 통신 프로토콜

→ 웹에서 요청(request)과 응답(response)을 주고 받는 약속된 방법

<aside>
👀

클라이언트(사용자)와 서버가 서로 통신하는 방법을 표준화한 프로토콜이다.

</aside>

그렇다면 프로토콜이란? 

→ 컴퓨터 간의 데이터를 주고 받는 방식을 정의하는 규칙 체계인데,

네트워크 상에서 데이터를 요리조리 전달 할 때, 

특정한 규칙을 갖춘 상태로 데이터를 넘겨야 원활한 소통이 가능하다. 

따라서 프로토콜은 데이터들을 일관적인 형태로 만들기 위한 틀이라고 생각하겠다.

→ **따라서 HTTP는 인터넷 상에서 클라이언트(사용자)와 서버 사이에서 서로 전달하는 데이터의 포장방식이라고 생각하면 된다**. 

<aside>
❓

예시를 들어서 이해해보자!

어떤 예약 사이트가 존재한다고 가정하자. 그 예약 사이트는 버스 좌석 예매 사이트이다. 내가 사용자로써 해당 사이트를 접속해서 특정 자리를 선택했다고 하자.

여기서 클라이언트(나)가 버스 좌석을 선택하는 행동을 함으로써 

웹 브라우저가 웹 서버에게 특정한 데이터를 넘겨주었을 것이다. 특정 데이터는 어떤 형태인지 명확하지 않지만, 이때 HTTP가 요청의 형태로 쓰였다는 사실은 명확하다.

</aside>

- HTTP의 성질
1. 비연결성 : 요청 혹은 응답의 메세지를 보낸 후에 바로 연결을 끊는다.
2. 무상태 : 요청 하나하나를 독립적으로 처리해서 서버가 클라이언트의 과거 요청을 기억하지 않는다. 

Q: 그런데 보통의 웹 사이트는 로그인 기능을 가지고 있고 로그인 상태를 유지해서 이 권한으로 페이지 접근 권한을 얻는데…? 

A: HTTP의 무상태를 해결하기 위해 “쿠키” 혹은 “세션”을 사용한다. 쿠키는 브라우져(클라이언트)에 사용자의 상태를 저장하고 세션은 서버에 사용자의 상태를 저장한다.

## 2. HTTP의 형태에는 어떤 것인가?

- 종류
1. 요청의 형태 = request
2. 응답의 형태 = response

이렇게 두 형태가 존재한다. 요청 메세지와 응답 메세지는 조금 다른데, 요청 메세지는 클라이언트가 서버에게 보내는 것이고 응답 메세지는 서버가 클라이언트로 보내는 대답이다.

→ 위의 예시에서 버스 예약 사이트를 가정했다. 버스 좌석을 선택했을 때, 클라이언트가 서버에게 지금 사용자가 버스 예약을 행하려 한다는 요청의 메세지를 보냈을 거고, 서버는 이를 처리하여 성공 혹은 실패의 정보를 다시 클라이언트가 볼 수 있도록 웹 브라우저에 정보를 띄울 것이다.

- HTTP Method

→ 서버가 수행해야 하는 동작의 정보를 담았다. 
어려운 말인 것 같아서 다시 설명하면, 우리가 웹 서버에 요청하는 수행 동작은 생각보다 구분할 수 있도록 종류가 정해져 있다고 이해하면 된다!

> 웹 서버야! 이 글 정보 조회해줘!  → GET
> 

> 웹 서버야! 이 글 게시해줘! → POST
> 

> 웹 서버야! 이 글 싫어! 삭제해줘!  → DELETE
> 

### A. GET 메소드

: 정보를 조회하기 위해서 사용한다. (게시글 조회, 회원 정보 확인과 같은 것들이 존재한다.)

→ **해당 요청에서는 서버에 데이터 (무엇을 조회할 것인가에 대한 키워드)를 전달하는 경우, 쿼리스트링을 통해 전달한다. 네이버에 “한국외대”를 조회할 때, 위의 URL을 찾아보면** 

**→ “query = 한국외대”, 이렇게 끝부분에 존재하는 쿼리스트링을 확인할 수 있다.** 

<aside>
❓

**쿼리스트링이란**….

URL의 가장 마지막 부분에 붙는 문자열로, ?로 시작하고 key = value 형식의 매개변수들이 &로 구분되어 서버에 전달됩니다. 

→ 그러면, 민감한 정보나 많은 양의 데이터를 조회할 때는 쿼리스트링을 사용하면 안된다는 점을 알 수 있다.

1. 민감한 정보가 쿼리스트링을 통해 브라우저 화면에 그대로 노출되기 때문이고
2. 방대한 데이터를 조회하는 경우에는 url의 길이 제약이 존재하기 때문이다.
</aside>

→ 쿼리 파라미터의 형식이란 “key = value” 형태이다.

데이터를 메세지 바디에 담아 전달하므로 get과 달리 내용의 용량상의 제약도 없다.

: 이들 중에서 클라이언트가 데이터를 주고 받기 위한 통신 통로가 api이라고 이해하면 된다.

→ 그래서 **api 명세서에는 어떤 요청인지 (HTTP 메서드)** 

**→ 어떤 주소로 보내야 하는지 (URL)**

**→ json으로 보내야 하는지, form-data 타입인지 명시하고**

**→ 응답의 종류 (성공 혹은 실패, 실패의 경우 어떤 원인 때문에 실패인지 알린다.)**

→ *http 응답에서 더 자세히 알아본다.*

위와 같은 정보들을 기능에 맞게 정리해놓은 것이라고 볼 수 있다.

### C. PUT 메소드

: 리소스 생성 / 업데이트하기 위해서 서버로 데이터를 보낼 때 사용한다.

- 전체 교체를 할 때 사용 → “갱신”의 목적으로 쓰인다. 즉, 기존의 자원의 정보가 새로운 자언으로 완전히 대체된다.
- 따라서 기존의 자원이 무엇인지 알기 위한 고유 ID가 URL에 포함되어야 한다.

ex) PUT/user/123 : 아이디가 123인 사용자의 정보를 수정하는 것

ex) PUT/board/1 : 보드 번호 1번의 정보를 수정하는 것

- 요청의 형식

Content-Type: application/json

{
"name": "다영",
"email": "pdayoung0402@hufs.ac.kr"
}

- 클라이언트는 수정할 부분의 필드만 서버로 보내고, 서버는 이 필드의 데이터만 수정한다.

## 3. HTTP 상태 코드

- 상태코드 : 서버가 클라이언트 요청에 대해 어떤 결과를 돌려주는지 나타내는 숫자로, 숫자에 따라서 담긴 의미가 다르다.
- 요청이 성공적으로 처리되면 200번대가, 문제가 발생하면 400번대와 함께 이유도 함께 리턴된다.

<aside>
👀

- 숫자 + 의미
1. 200 OK → 요청 정상 처리 성공
2. 201 Created → 새로운 리소스 생성 성공
3. 400 Bad Request → 잘못된 요청, 잘못된 이메일 형식이나 누락된 정보 존재
4. 401 Unauthorized → 권한 없음. 인증 실패
5. 403 Forbidden → 접근 거부. 인증은 되었지만 너는 못 가!!!
6. 404 Not Found → 리소스 없음
7. 500 Internal Server Error → 서버 내부 에러
</aside>

- **401(인증 실패)와 403(접근 거부)에 관해서**

**: 401은 사용자 로그인을 하지 않아서 인증이 필요한 경우** 

**→ 입장키를 가지고 기계에 찍었지만, 너는 등록된 사람이 아니야!!**

**: 403은 사용자가 인증은 되어 있지만, 특정 자원에 접근할 권한이 없는경우**

**→ 입장키를 가지고 기계에 찍어서 “넌 00이구나!, 근데 못 들어가!!!”**

} // 이메일 형식이 틀려서
